# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

astro-myst brings MyST Markdown to Astro as an **integration plus a content loader**. It does **not** parse MyST itself: for each collection it generates a MyST project in Astro's cache folder, runs the official `mystmd` CLI (`myst build --site`) on it, reads the fully resolved per-page JSON AST, renders it to HTML and stores one content-layer entry per file. All MyST semantics (numbering, cross-page references, citations and DOIs, KaTeX, includes, notebooks, LaTeX parsing) come from mystmd; this package maps nodes to HTML, rewrites MyST URLs into Astro URLs and handles assets. Users never write a `myst.yml`, and nothing is written next to their content or into `public/`.

It is an npm-workspaces monorepo. The published package is `packages/astro-myst`. `examples/{minimal,book,paper}` and `docs/` (the documentation site, written in MyST and rendered by astro-myst itself) import the package's **built** `dist/`, so run `npm run build` before building or type-checking them.

## Commands

Node >= 22.22 (what the Astro version in the lockfile needs; the published package itself supports 22.12), npm >= 10.9. Run from the repo root.

```sh
npm ci && npm run build        # the build is required before docs/examples/typecheck
npm run lint                   # Biome lint + format check (lint:fix applies fixes)
npm run typecheck              # tsc for the package and e2e, astro check for docs and examples
npm test                       # vitest; integration tests run the real mystmd (~20 s)
npm test -w astro-myst -- test/urls.test.ts -t "routeFor"   # one file / one test
npm run test:coverage          # thresholds in packages/astro-myst/vitest.config.ts
npm run examples:build && npm run docs:build && npm run test:e2e  # Playwright: built sites + the minimal example in `astro dev`
npm run check:package          # publint + Are the Types Wrong
npm run dev -w astro-myst-example-book   # live example (npm run docs:dev for the docs)
```

In Claude Code cloud containers, point Playwright at the preinstalled browser instead of downloading one: `PLAYWRIGHT_CHROMIUM_EXECUTABLE=/opt/pw-browsers/chromium npm run test:e2e`. Astro 7's `astro dev` may detach into a background daemon there; use `npx astro dev status|logs|stop` in the example folder to inspect or stop it.

## Public API

- `astro-myst` (root, kept light for astro.config: ~15 ms to import): default export `myst(options)` integration, the pure navigation helpers `mystNavigation(entries)` / `mystPrevNext(entries, current)` for pages, types, `VERSION`.
- `astro-myst/loaders` (imported by `src/content.config.ts`, like `@astrojs/starlight/loaders`): `mystLoader`, `mystSchema`, `renderMystPage`, `compileMystProject`, `readMystBuild`. The loader imports the compiler and renderer **statically**: Astro 5 closes the Vite module runner that evaluated the content config before loaders run, so `import()` inside `load()` fails there.
- Stylesheets `astro-myst/base.css`, `/theme.css`, `/katex.css`; component `astro-myst/XrefPreview.astro`; browser scripts `astro-myst/client/{sync-tabs,copy-code,mermaid}` (side-effect modules, listed in `sideEffects`), normally injected by the integration's `scripts` option.

## Architecture (`packages/astro-myst/src`)

Pipeline per collection: **discover files** → **generate project** → **compile** (mystmd) → **render** (AST → HTML) → **publish assets** → **store**.

- `integration.ts` — `myst(options)`. `astro:config:setup` stores options in the shared state, injects the stylesheets with `injectScript('page-ssr', …)` (`styles: 'base' | 'theme' | false`) and the browser scripts with `injectScript('page', …)` (`scripts`: `syncTabs` on by default, `copyCode` and `mermaid` opt-in; mermaid is an optional peer dependency, dynamically imported only on pages with a diagram; `src/client/mermaid-module.d.ts` types it without a dependency); `astro:server:setup` adds the dev middleware serving `<base>/_myst/<collection>/<file>`; `astro:build:generated` copies every collection's assets into the output (client dir for server output), with an idempotent repeat in `astro:build:done`. Copying in `build:generated` matters: adapters are unshifted to the front of the integration list, so their `build:done` (which packages the output) runs before ours.
- `state.ts` — integration ↔ loader state on `globalThis[Symbol.for('astro-myst.state')]`: astro.config and content.config are separate module graphs, so module-level variables are not shared.
- `project.ts` — `findSources` (tinyglobby; default pattern `**/[^_]*.{md,ipynb}`; `IGNORED_DIRS`), `readFrontmatter` (YAML core schema + timestamps, like Astro), `entryIdFromPath` (identical to Astro's `glob()` ids — tested against Astro's own function), `createProjectConfig` (the generated myst.yml: toc entries pointing at the files via relative paths, user `toc` mapping with `pattern` expansion and unlisted files appended, a placeholder `index.md` root page when the collection has no index, project-option file paths rewritten from Astro-root-relative to project-relative, `.bib` auto-discovery in `base`). With `--execute` and an executable file (`.ipynb`, or `.md` with a `kernelspec`), every toc file is listed through `<projectDir>/source`, a symlink (junction on Windows) to `base`: mystmd's Jupyter server is rooted at the project folder and refuses `../` paths, and listing all files through it keeps relative links between pages consistent. `writeProject` keeps/creates/removes the link (never recursive-delete it: it points at user content); `sourceFileOf` maps page locations back. Exports are declared as **project-level** exports in the generated myst.yml (one per page and format, `articles: [file]`, plus whole-collection ones) with `output` under `_build/exports/astro-myst/<format>/`: page-frontmatter `output` paths resolve next to the page, so astro-myst never uses them and the loader refuses them for enabled formats.
- `exports.ts` — the `exports` option (`['pdf', …]` or `{ pages, collection, templates, dev }`), merged integration → loader, resolved to `undefined` in dev unless `dev: true`; format table (mystmd format, `myst build` flag, output extension: tex → `.zip`, typst → `.pdf`, jats → `xml`). Templates for pdf/tex/typst/docx are downloaded by mystmd from api.mystmd.org (blocked in Claude cloud containers), so tests run md and jats only.
- `navigation.ts` — `mystNavigation` (tree from `data.myst.order` + `data.myst.parents`, groups keyed by title, pages by id) and `mystPrevNext`.
- `loader.ts` — `mystLoader()` (`satisfies Loader` so collections infer data types). Requires the integration's state. Generated project lives in `<cacheDir>/astro-myst/<collection>/` (`myst.yml`, `_build/`, `assets/`). Cache: fingerprint of inputs (base + `extraInputs` + files referenced by `project`, by path/size/mtime) + VERSION + mystmd label + args + generated yaml, in the loader's `meta`; unchanged → `readMystBuild`. Two passes: map each page (`sourceFileOf(location)`; placeholder skipped) to its source file, id, URL and toc ancestors (mystmd's `config.json` pages include title-only group entries); then render, tracking assets used via `resolveAssetUrl` and building `data` = raw frontmatter + MyST-normalized keys + `myst: { url, order, level, enumerator, kind, parents, parts?, downloads?, exports? }`. Exported files are published into `assets/exports/<format>/<entry id>.<ext>`; a missing export throws in build, warns in dev; `_build/exports/astro-myst` is wiped before each compile. `sync()` renders everything before mutating anything, then publishes used assets atomically into `assets/` and replaces the store. Without a watcher (`astro build`) errors throw with an `[astro-myst]` prefix; with one (`astro dev`) they are logged and the previous entries stay. Dev: any change under the inputs recompiles the collection (200 ms debounce, queued) — intentional, numbering is global.
- `compile.ts` — runs mystmd (`resolveCommand`: `command` option, else the `mystmd` npm package from the Astro root / project / this package, else `myst` on PATH), seeds a stub site template so `myst build --site` never downloads MyST's React theme, wipes `_build/site`, serializes builds per project, classifies output (`⚠️` warn, `⛔`/`error` error; mystmd's "'frontmatter' extra keys ignored" warnings are hidden because those keys are the site's own). `readMystBuild` checks the page format `version` against `SUPPORTED_PAGE_VERSIONS`.
- `render.ts` — `MystRenderer`, a `switch` in `builtin()` mapping MyST nodes to hast (hastscript), serialized with `allowDangerousHtml` (mystmd supplies KaTeX and citation HTML). User `handlers` first (`undefined` → built-in, `null` → nothing, `ctx.renderDefault` to wrap). Unknown nodes fall back to `div`/`span.myst-<type>`; never throw on new node types. Shiki: highlighter cached per theme pair, only used languages loaded, inline light colours (`defaultColor: 'light'`; base.css switches to dark). Footnotes and bibliography appended per page (the bibliography goes where a `{bibliography}` node is, if any). Frontmatter `parts` (not in the mdast) are rendered too: abstract/summary/keypoints before the content, others after, and returned as `parts`. Blocks with `data.part` render as `section.myst-part`, except `toc:<context>` parts (`{toc}`), which become `nav.myst-toc`. Notebook outputs in both the mystmd ≥ 1.7 (`jupyter_data`) and older formats.
- `assets.ts` — dev middleware (strips `base` if still present, path-traversal guard, falls through to the next handler when missing), `copyAssets`, content types.
- `schema.ts` — `mystSchema` (`.catchall(z.unknown())` so authors' own keys pass; `date` coerced to `Date`).
- `urls.ts` — `routeFor` (prefix or function; `index` entry at the prefix), `pageUrl` (base + trailingSlash), `assetUrl`.
- `components/XrefPreview.astro` — client-side custom element; on hover/focus of `a.myst-xref, a.myst-cite` it fetches the target page and shows the target element as a tooltip.

## Conventions and gotchas

- **Feature matrix**: `docs/content/reference/myst-features.md` lists every MyST/mystmd feature by category (input formats, roles, directives, references, math, citations, notebooks, structure, frontmatter, exports, site, interactivity, extending) with its status in astro-myst. Update it in the same change whenever support changes, and only mark what was verified (compile a test page with the real mystmd and check the HTML). Interactivity (Thebe, widgets, anywidget) is deliberately out of scope for now.
- **The rendered HTML is a public contract.** Every class the renderer emits starts with `myst-` (injected CSS must never clash with site or Tailwind classes such as `grid`, `card`); exceptions: `mermaid`, Shiki's `shiki`/`line`/`highlighted`, `task-list-item`, `language-*`, and classes authors set (including MyST's own `button`). Tests assert exact HTML (`render.test.ts`, `latex.test.ts`, `doi.test.ts`), `styles/*.css` and `XrefPreview.astro` depend on the classes, and `docs/content/reference/components-and-styles.md` documents them. Change them together.
- **CSS**: every selector in `base.css` and `theme.css` is wrapped in `:where()` (zero specificity) and sits in `@layer components`, after the statement `@layer theme, base, components, utilities;` (Tailwind 4's order): users' CSS, Tailwind utilities and `prose` (in `utilities`) win, while Tailwind's preflight (`base`) cannot reset our margins and borders, whichever stylesheet loads first. Only the KaTeX overrides stay unlayered, because katex.css is; `base.css` holds only what content needs to work, the look goes in `theme.css`. `!important` appears only where Shiki's inline styles must be overridden for dark mode (file-level biome-ignore).
- **Entry data**: keys MyST knows (`title`, `authors`, `date`, `thumbnail`, …) come normalized from mystmd and override the raw values; any other frontmatter key is kept as written (mystmd drops unknown keys, so the loader reads raw frontmatter itself). Computed values live under `data.myst`, never at the top level, so they cannot collide with authors' keys.
- Integration tests copy a fixture (`test/fixtures/<name>`) to a temp folder; tests never build inside the repo. `fixtures/collection` (no myst.yml) drives the loader tests through the real integration hook (`setupIntegration` in `test/helpers.ts`) and a fake `LoaderContext`; `basic`, `latex`, `doi` are plain MyST projects for `compile.ts`/renderer tests. The DOI test seeds mystmd's `_build/cache` to stay offline.
- `src/version.ts` is generated by `scripts/sync-version.mjs` (on `prebuild` and in `npm run version-packages`); do not edit it.
- `test/readme.test.ts` keeps the README's custom-handler example working. The root `README.md` and `packages/astro-myst/README.md` (shown on npm) are separate near-copies; keep them in sync.
- `katex` is a dependency only for its CSS (`styles/katex.css`); mystmd renders math with its own bundled KaTeX (0.15.6 as of mystmd 1.11). It is pinned to exactly that version and Dependabot ignores it: newer KaTeX renames the classes in mystmd's math HTML, so never upgrade it on its own. `test/katex.test.ts` fails when mystmd bundles a different version.
- A new mystmd page format: test it, then add the version to `SUPPORTED_PAGE_VERSIONS` in `compile.ts`. A new Astro major: add it to `peerDependencies` and to the `compat` matrix in `.github/workflows/ci.yml`.
- `peerDependencies` (astro, mystmd, the optional mermaid) are a promise to users, pinned by `test/peer-dependencies.test.ts`. Dependabot *replaces* a peer range when it moves a workspace to a new major (mermaid `^10.0.0 || ^11.0.0` became `^12.2.0`), so that test fails on such PRs: widen the range instead (old majors stay), add a changeset, update the test. Several Dependabot PRs touching `package-lock.json` conflict with each other; combining them in one branch (merge each, let `npm install --package-lock-only` resolve the lockfile conflicts) needs one CI run; once those commits reach main, GitHub shows the Dependabot PRs as merged (Dependabot closes any it rebased in the meantime).
- Changes to the published package need a changeset (`npx changeset`; patch, minor or major). Docs, examples and CI changes do not. Releases are automated (a Changesets "Version Packages" pull request, then npm trusted publishing); see `MAINTAINING.md`.
- Style is enforced by Biome: 2 spaces, single quotes, trailing commas, semicolons, 120 columns. `noExplicitAny` is off because the MyST AST is loosely typed (`MystNode` has `[key: string]: any`). ESM with `.js` import specifiers (NodeNext).
- Generated and git-ignored: `_build/`, `public/_myst/` (old layout), `public/pagefind/`, `dist/`, `node_modules/.astro/` (holds the generated MyST projects). mystmd's asset file names (`name-<hash>.ext`) differ between checkouts even for identical content, so never commit them.

## CI

`ci.yml` runs Biome, type checks, tests on Ubuntu (Node 22/24/26), macOS and Windows, package checks, a compat job and Playwright e2e, plus zizmor. Keep path handling and process spawning cross-platform (`compile.ts` handles Windows `.cmd` shims; generated toc paths are POSIX). The compat job builds the book example from the packed tarball against Astro 5/6/7 and mystmd 1.3/1.8/latest, so older Astro and mystmd versions must keep working. Actions are pinned to commit SHAs (local actions use GitHub's `$/` syntax, which actionlint 1.7 does not know yet). A CI `scope` job runs `.github/scripts/release-only.mjs`: for release-only changes (the Changesets "Version Packages" PR and its merge: deleted changesets, changelogs, `"version"` lines, `VERSION`) the expensive jobs are skipped via job-level `if`, and the final `CI OK` job (the only required check) passes when every job passed or was skipped. CodeQL and the docs build skip the `changeset-release/main` PR; `release.yml`'s pack job still tests before publishing. `release.yml` opens that PR with `GITHUB_TOKEN` (which triggers no workflows) and then starts CI on the branch with `gh workflow run` (`workflow_dispatch` is the exception); for `workflow_dispatch`, `scope` compares HEAD with its merge base on the default branch. No GitHub App or PAT is needed. The docs workflow runs on pushes and PRs only for paths the site depends on.

Limitations by design (`docs/content/explanation/limitations.md`): static output only, one MyST project per collection, a full recompile of a collection on every change, and MyST theme site options do not apply (the Astro layout is the theme).
